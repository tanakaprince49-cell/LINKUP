# Custom-domain app and Payonify return fixes — 16 October 2026

## Coordinated fixes

### Marketing repository: Linkup-landing-page

Both `/app` and `/app/` now target the upstream `/index.html` explicitly before the existing prefix-stripping wildcard proxy. This fixes the trailing-slash entrance that previously returned marketing HTML. Other app routes, assets, APIs, public profile pages and PWA files continue to proxy to the live LINKUP app deployment. Marketing routes, DNS and domains are unchanged.

The marketing robots file now advertises the app profile sitemap alongside the existing marketing sitemap. The footer links to `/app/builders`, and that URL is added to the existing marketing sitemap copies. Search Console verification/submission remains a domain-owner action.

### App repository: LINKUP

`api/_webReturns.js` resolves payment returns using supported browser origins. Custom-domain requests always use the `/app/` mount, including old cached clients that omit `appBasePath`. Original Vercel-root requests keep their root behavior; explicit `/app` requests on that origin remain supported.

`PAYONIFY_SUCCESS_URL` and `PAYONIFY_CANCEL_URL` overrides are now accepted only when they stay on the initiating origin and, for mounted clients, under `/app`. Stale old-domain overrides, marketing-root overrides and unsafe/non-HTTPS values fall back to the current app entrance. Valid same-origin app paths remain supported. Query strings/fragments are removed for Payonify's plain-URL validator, while `/app/` retains its PWA-safe slash.

This guards against stale environment configuration without reading out or changing production secrets. It keeps sessionStorage payment references and Firebase auth on their original browser origin. The supported production origins are `www.linkupbuild.com`, `linkupbuild.com`, and `linkup-muqu.vercel.app`; adding another production domain requires updating the allowlist.

A malformed signature-length guard was also added so invalid webhook signatures fail verification instead of causing `timingSafeEqual` to throw. Valid signature behavior and provider event processing are preserved.

## What did NOT change

- Payonify's registered webhook URL: keep `https://linkup-muqu.vercel.app/api/payonifyWebhook`.
- Payment API keys, webhook secret values, provider dashboard configuration or Firebase credentials.
- Subscription prices, transaction ownership checks, server-side entitlement authority or native Google Play billing.
- DNS, domain assignments or marketing root routes.

The custom-domain webhook alias remains `https://www.linkupbuild.com/app/api/payonifyWebhook`; there is no need to move provider registration away from the original stable endpoint.

## Verification

Local automated checks:

```sh
npm run test:payments   # return URLs + local HMAC signature fixtures
npm run test:seo
npm run test:web-paths
npm --prefix mobile run typecheck
```

The marketing build runs its routing regressions before Vite export; its TypeScript check also passes.

Safe production audit:

```sh
npm run verify:web-routing
# Optional: demand a particular deployed app revision
EXPECTED_APP_SHA=<commit-sha> npm run verify:web-routing
```

The audit compares actual app entry scripts and build markers across the upstream and `/app`, `/app/`, `/app/landing`, `/app/login`, and `/app/index.html`. It checks marketing isolation, app JS content type, PWA scope/worker, profile XML and authoritative root robots discovery. It GETs webhook endpoints (expect 405), and sends unauthenticated checkout/status POSTs (expect 401 before any transaction/provider operations). It never POSTs a fake webhook, signs into an account, creates a checkout or charges money.

The app deployment workflow runs unit/routing/type checks before production promotion and the live audit afterward. Thus a successful app-source push must both deploy and pass cross-domain revision checks; custom-domain updates are not a separate copied app build.

## Remaining end-to-end acceptance

HTTP reachability, mocked checkout payloads and local HMAC fixtures are not proof of a completed payment. With a signed-in account, perform an approved test-mode checkout, confirm the return remains on the initiating app origin, inspect an authentic signed provider delivery in Payonify's dashboard, and confirm PLUS/Campaigns entitlement activation. Real Google/email sign-in/out also needs a browser account test. No live purchase or real signed-provider event was generated by this release work.
